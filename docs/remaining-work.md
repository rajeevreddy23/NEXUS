A separate persistent Java Tasks application and operational recovery adapter have now been implemented. See [setup and behavior](real-application.md) and [API](api.md). Its new cloud acceptance must pass before it is reported as verified; previous demo results alone do not establish its correctness. Continuous hosting, real-world workload validation, broad statistical evaluation and institution-specific submission review remain separate from functional implementation.

## Required controlled-demo acceptance

No known blocker remains for the implemented single-controller, three-service academic demonstration. The verification ledger links actual cloud evidence for database migration, authentication, telemetry, all three faults, sandbox validation, approval protections, health verification, a populated browser graph and one enabled Spring AI/PGvector scenario. This is an ephemeral reproducible deployment, not continuously hosted infrastructure or a guarantee against all bugs.

## Hosting constraint

No paid service, credits, overage setting or Render resource was created. All runtime test containers and volumes were deleted by CI. There is no permanent public URL. Continuous hosting of the complete persistent architecture, including isolated sandbox/database and real observability services, remains a separate infrastructure decision requiring suitable compute. Do not describe a GitHub Actions run as continuous hosting.

## Deliberate limits

In the laboratory, recovery clears supported synthetic faults through RESET_FAULT. In application mode, it can resume maintenance-blocked traffic only after validation and approval. It does not repair arbitrary infrastructure or application code. The topology is declared, confidence is heuristic, sessions are process-local, one controller is supported, and the isolated database does not contain equivalent business data. Provider availability and free quotas can change. These are documented scope boundaries, not features silently removed for cloud testing.
